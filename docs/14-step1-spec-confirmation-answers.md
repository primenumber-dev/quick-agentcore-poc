# Step1 仕様確認シートへの回答(MCP・基盤アーキテクチャ設計)

作成日: 2026-09-02

---

### Q1. AgentCore Runtimeを使用した場合のOAuth検証エンドポイントについて

JWT検証用の`discoveryUrl`(`.well-known/openid-configuration`)は、Custom JWT Authorizerが直接参照するため独自実装不要。`.well-known/oauth-protected-resource`もAgentCore Runtimeが自動的に提供するため不要。ただし`registration_endpoint`のような追加のメタデータエンドポイントは、AgentCore Runtimeには任意のルートを追加できる層が無いため、そもそも実装できない。

### Q2. AgentCore Runtimeを使用した場合の呼び出しプロトコルについて

Claude CodeはOAuthメタデータURLやscopeをローカル設定で上書きできるが、Claude.ai Web版/Desktop版はクラウド側でOAuthを実行し固定コールバックURLを使うため上書き手段が無い。401応答にscopeを明示しないと、Web/Desktop版はサポートされる全スコープを要求してしまうため、Runtime側の許可スコープ設定を明示する必要がある。また、カスタムコネクタ追加には組織のOwner権限が必要な場合がある(プラン依存)。Desktop版固有の検証は未実施。

### Q3. ShimとOpenAPI準拠のロジックについて

Shim(アプリケーションロジック)はコンテナ内処理のため、AgentCore Runtimeに変更しても無変更でそのまま動作する。一方、「API Gatewayのmock統合=OpenAPI準拠API提供」という前提は実態と異なり、実際はOAuthメタデータをCognitoにプロキシするための仕組みである。Custom JWT Authorizerは「JWTの検証方法」を設定するものであり「対応API仕様」を指定する機能を持たないため、そのような対応自体が不要(設定項目として存在しない)。

### Q4. AgentCore Runtimeを使用した場合のリクエストヘッダーの扱いについて

対処が必須。PoC(API Gateway経由)は、検証済みの値でヘッダーを強制上書きする仕組みがあるため「無条件に信頼する」設計でも安全だが、AgentCore Runtimeには同等の上書き保護が存在しない。実機で、有効な自分のJWTを持つ利用者が`x-cognito-sub`ヘッダーを書き換えるだけで別テナントになりすませることを確認した。対処はAgentCore Runtimeの許可ヘッダー一覧から`x-cognito-sub`を除外するだけで済み、アプリコードの変更は不要(ヘッダーが無ければBearerトークンから`sub`を導出するフォールバックが既にあるため)。あわせて、現状署名検証をしていないJWTデコード処理の強化も推奨する。

### Q5. AgentCore Runtime の利点について

「アプリケーション側で状態保持を実装する必要がない」という点は正しい。ただし「マイクロVM単位のセッション隔離機能自体が不要」は言い過ぎで、ステートレスなMCPサーバーのままでも、セッションIDによるマイクロVMスティッキーロイティングには対応しており、正しく活用すればコンテナ起動コストの削減(レイテンシ改善)につながる可能性がある。この効果自体は未検証。

### Q6. AgentCore RuntimeのInboundについて

Outboundの閉域化(VPCモード)は実機で問題なく動作することを確認済み。ただしInboundは、VPCモードにしてもAWSの共通パブリックエンドポイントのままで変わらない。真に閉域化されたインバウンドを実現するにはPrivateLink接続が必要になると考えられるが、これは未検証。閉域網要件が出てきた際にネックになりうるというご懸念は妥当と考える。

### Q7. MCPプロトコルバージョンv2(2026-07-28)対応SDKへのアップグレードについて

「2026-07-28」は実在する正式なMCP仕様のリビジョンで、プロトコル発表以来最大の改訂と位置付けられている。現在のSDK(`2025-11-25`まで対応)からは、`initialize`ハンドシェイクの廃止・`Mcp-Session-Id`のプロトコルコアからの除外を含む、配線レベルの破壊的変更を伴うメジャーアップグレードになる。

ご認識の通り、v2対応の新SDKは「MCPクライアント側のバージョンによらず利用できる」ことをデフォルトの設計方針としている。新しいサーバー実装(`createMcpHandler`)は、旧世代(`initialize`ハンドシェイクを使うクライアント)と新世代(自己申告方式のクライアント)を同一エンドポイントで自動的に振り分けて処理する。ただし、これは**SDKのバージョンを上げるだけで自動的に手に入るものではなく**、新しいAPIの書き方(サーバー実装の構成)へ移行することが前提になる点に注意が必要。

現時点でv2対応の公式TypeScript SDKはベータ版であり、今すぐ追随すると仕様の変動に追従し続けるコストが発生する。AWS側(AgentCore Runtime)は既に2026-07-28に言及しており、ホスティング側の対応は先行しているため、ボトルネックはSDKのベータ状態にある。GA(正式版)を待ってから、独立した移行プロジェクトとして計画的に実施することを推奨する。
