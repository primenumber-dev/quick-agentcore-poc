# コストシミュレーション: パターン3(AgentCore Runtime) vs パターン4(API Gateway + ECS)

> **この章で分かること**
> 「常時起動」と「実行中のみ課金」という2つの料金モデルが、実際の月額コストにどう跳ね返るかを試算する。結論から言うと、低〜中トラフィックではパターン3が一桁以上安い。損益分岐点がどこにあるかも示す。

作成日: 2026-08-17

> **注意**: 本シミュレーションは公開されている料金表(2026年8月時点、`ap-northeast-1`)を基にした概算であり、正式な予算確定前には[AWS Pricing Calculator](https://calculator.aws)等での再検証を推奨する。特にAgentCore Runtimeは比較的新しいサービスで料金改定の可能性がある。
>
> 関連: [01-architecture-comparison.md](./01-architecture-comparison.md)で示した構成図・プロコンの数値的な裏付けにあたる章。

## 前提となる料金

### パターン3: AgentCore Runtime
実行中(アクティブCPU使用時間)のみ課金。アイドル時間(外部API応答待ち等のI/O待機)は無課金。

- vCPU: **$0.0895 / vCPU時間**(実使用時間ベース、秒単位課金)
- メモリ: **$0.00945 / GB時間**(セッション時間ベース、128MB下限)
- セッションあたり最低1秒課金

### パターン4: API Gateway + ECS(既存構成、常時起動)

現在デプロイされている構成をベースに算出:

| 項目 | 単価(概算) | 備考 |
|---|---|---|
| Fargate vCPU | $0.0506 / vCPU時間 | 0.25 vCPU、常時起動 |
| Fargate メモリ | $0.00553 / GB時間 | 0.5 GB、常時起動 |
| ALB | $0.0243/時間(固定)+ LCU使用料 | 常時起動 |
| NATインスタンス(t3.nano)× 2 | 約$0.0068/時間 × 2台 | 常時起動、EC2代のみ(データ転送量別) |
| API Gateway(HTTP API) | 約$1 / 100万リクエスト | 従量課金 |
| DynamoDB(PROVISIONED 5RCU/5WCU) | 約$0.3/月 | 両パターン共通・無視できる規模 |
| CloudWatch Logs | 約$1〜2/月 | ログ量に依存、両パターンでほぼ同等 |

## シミュレーション結果(月額試算)

前提: 1リクエストあたりのアクティブCPU時間を保守的に1秒と仮定(AgentCore側の最低課金単位に合わせた仮定。実際のツール呼び出しは外部QUICK API待ちのI/O時間が大半を占めるため、実測ではさらに安くなる可能性が高い)。

| 月間リクエスト数 | パターン3: AgentCore Runtime | パターン4: API Gateway + ECS |
|---|---|---|
| 10,000件 | 約 $0.08 | 約 $46 |
| 100,000件 | 約 $0.75 | 約 $46 |
| 1,000,000件 | 約 $7.5 | 約 $47 |

- **パターン4はリクエスト数に関わらずほぼ固定費**(Fargate常時起動 約$11 + ALB 約$24 + NATインスタンス 約$10)。このPoC規模(desiredCount=1)では月額**約$46**が"起動しているだけ"で発生するベースコストになる。
- **パターン3はリクエスト量に完全比例**し、リクエストが無い時間帯は実質$0。低〜中トラフィックのPoC/検証フェーズでは圧倒的に安い。

## 損益分岐点(概算)

上記の仮定(1リクエスト=1秒のアクティブCPU時間)のもとでは、月間**約610万リクエスト**を超えたあたりで、パターン4(常時起動)の固定費の方が相対的に割安になり始める計算になる。

```
損益分岐点 ≈ (パターン4の月額固定費) / (パターン3の1リクエストあたりコスト)
          ≈ $46 / $0.00000753
          ≈ 約610万リクエスト/月
```

平常時のクライアント想定トラフィック(社内利用中心のMCPツール呼び出し)であれば、この規模に達する可能性は低く、**パターン3(AgentCore Runtime)の方がコスト効率で優位**と考えられる。

## レイテンシ実測(2026-08-21実施)によるアクティブCPU時間の再検討

[03-agentcore-runtime-verification.md](./03-agentcore-runtime-verification.md)で、リクエストの**壁時計時間(クライアントからみた応答時間)** を実測したところ、アイドル時間0秒〜16分の範囲で一貫して約6秒だった(コールドスタートによる有意差は無し)。

ただし、この6秒を単純に「1リクエストのアクティブCPU時間」として上記シミュレーションの`1秒`の代わりに使うのは**不適切**。理由:

- AgentCore Runtimeの課金は「アクティブCPU使用時間」のみで、外部API/DynamoDB/Cognito JWKS取得などの**I/O待機時間は無課金**とされている。壁時計6秒の内訳(CPUバウンド処理 vs I/O待機)を分解できていないため、実際の課金対象時間は6秒より大幅に小さい可能性がある
- AgentCore Runtimeの実際のvCPU/メモリ割り当て量(Fargateのように明示的にサイズを指定する項目がAPI上に見当たらない)も未確認のため、時間単価への当てはめ自体に不確実性が残る

**結論**: 既存の「1リクエスト=1秒」という保守的仮定は、裏付けとなる実測課金データが無い以上、現時点では変更しない(下方修正の余地はあるが上方修正が必要という証拠もない)。**正確なコストを出すには、実際にリクエストを一定量流した上でAWS Cost Explorerの`Bedrock AgentCore`サービス実績を確認するのが最も確実**であり、これを次のステップとして推奨する。

## 留意点・シミュレーションの限界

1. **実際のアクティブCPU時間(課金対象)は未計測**。壁時計レイテンシ(約6秒、上記参照)は実測したが、課金対象のアクティブCPU時間とは別物。今回のPoCコードは外部QUICK API呼び出しを含むため、実際の「待ち時間」が多いほどAgentCore側はさらに安くなる。逆に大量データ処理などCPUバウンドな処理が増えると、この試算より高くなる可能性がある。
2. **ALB/NATインスタンスのデータ転送量は含んでいない**(トラフィック次第で追加費用が発生)。
3. **Cognitoの料金は考慮していない**(現状の利用規模では無料枠内に収まる可能性が高いが未検証)。
4. **可用性要件(マルチAZ、冗長化)を厳密に揃えていない**。パターン4は既にマルチAZ構成、パターン3(AgentCore Runtime)の可用性特性は別途確認が必要。
5. **モデル推論コスト(Bedrock LLM呼び出し)は両パターンに共通のため比較対象外**としている。
6. **VPCモード(閉域網対応)にする場合、追加の固定費が発生する**(2026-08-21実施のVPCモード実機検証[05-security-compliance-verification.md §4.1.1](./05-security-compliance-verification.md)で判明)。S3・DynamoDBのGatewayエンドポイントは無料だが、コンテナイメージpullに必要なECR用Interfaceエンドポイント(API/DKRの2種)は**エンドポイントごと・AZごとに時間課金**が発生する(2エンドポイント×2AZ=4ENI相当)。閉域網訴求時のコスト試算にはこの固定費を追加する必要がある。

## VPCモード・WAFを含めた1ヶ月コスト試算(2026-08-25追加)

「閉域網対応(VPCモード)」「WAF導入」をどちらも行う、金融グレードの本番展開に近い構成同士で比較する。追加費用の単価は`ap-northeast-1`のAWS公開料金表に基づく概算(2026年8月時点)であり、正式な予算確定前には[AWS Pricing Calculator](https://calculator.aws)での再検証を推奨する。

### 追加費用の単価(概算)

| 項目 | 単価(概算) | 対象 |
|---|---|---|
| VPCエンドポイント(Interface型、ECR API/DKRの2種×2AZ) | $0.014/時間/AZ | パターン3をVPCモードにする場合のみ |
| WAFv2 Web ACL(固定費) | $5/月 + ルール1本あたり約$1/月 | 両パターン共通(WAF導入時) |
| WAFv2(リクエスト従量) | 約$0.60 / 100万リクエスト | 両パターン共通(WAF導入時) |
| CloudFront(パターン3のWAF代替構成に必須) | 約$0.75/100万リクエスト(リクエスト分)+ 約$0.11/GB(データ転送分) | パターン3をWAF対応にする場合のみ |

パターン3(AgentCore Runtime)はWAFを直接アタッチできないため、CloudFront経由の代替構成([05-security-compliance-verification.md §4.5](./05-security-compliance-verification.md)参照)が前提となり、CloudFrontの費用も追加で乗る。パターン4(API Gateway + ECS)は既にVPC内にあり、WAFはAPI Gatewayへの直接アタッチを想定するためCloudFrontは不要。

### 試算結果(月額、閉域網+WAFを両方導入した場合)

| 月間リクエスト数 | パターン3(AgentCore、VPCモード+WAF/CloudFront) | パターン4(ECS、WAFのみ追加) |
|---|---|---|
| 10,000件 | 約 $46 | 約 $52 |
| 100,000件 | 約 $47 | 約 $52 |
| 1,000,000件 | 約 $55 | 約 $54 |
| 5,000,000件 | 約 $93 | 約 $60 |

VPCモード(約$40/月)とWAF(約$6/月)の固定費が加わることで、パターン3の月額固定費(約$46)がパターン4の固定費(約$46)とほぼ同水準になる。その上でパターン3は依然リクエスト量に比例した従量費用が乗るため、**両方の閉域網・WAF要件を満たす構成同士で比較すると、損益分岐点は当初の約610万リクエスト/月から、約77万リクエスト/月まで大幅に下がる**。

```
損益分岐点(閉域網+WAF込み) ≈ (パターン4固定費 - パターン3固定費) / (パターン3従量費 - パターン4従量費)
                          ≈ (52 - 46) / (0.0000094 - 0.0000016)
                          ≈ 約77万リクエスト/月
```

**重要な所見**: 「AgentCore Runtimeは低トラフィックなら圧倒的に安い」という結論(§上記)は、**閉域網対応やWAF導入を前提にしない場合に限られる**。金融グレードでの本番展開を見据えてセキュリティ要件(VPCモード・WAF)を満たそうとすると、パターン3の固定費がパターン4に近づき、実質的な損益分岐点は1桁近く下がる。想定トラフィック量によっては、セキュリティ要件を満たした状態でのコスト優位性はパターン3側に無いか、むしろパターン4が有利になる可能性がある。この点は、コスト面の結論を提示する際に必ず添えるべき重要な留保である。

## 結論(たたき台)

- **低〜中トラフィックのPoC・初期展開フェーズ、かつ閉域網・WAF要件が無い場合**: パターン3(AgentCore Runtime)がコスト面で明確に有利、かつインフラ構築・運用の手間も少ない
- **閉域網対応(VPCモード)・WAF導入をどちらも要件とする場合**: 損益分岐点は約610万リクエスト/月から約77万リクエスト/月まで下がる。想定トラフィック量次第では、パターン3のコスト優位性は無くなるか、パターン4が有利になる
- **将来的に大量トラフィックが見込まれる場合**: どちらの損益分岐点を使うべきかは、セキュリティ要件の有無で変わるため、まず要件を確定させる必要がある
- 最終判断には、実測ベースのアクティブCPU時間、想定トラフィック量、可用性要件、閉域網・WAF要件をクライアントと合わせてすり合わせることを推奨
